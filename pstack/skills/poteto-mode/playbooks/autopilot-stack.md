### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear Graphite stack they review and land.** For "autopilot-stack", "stack them, don't ship", and "build the stack, I'll land it". The owner loop and verification gate match **Autopilot-full**; only the terminal action differs.

1. **Run the owner loop without merge authority.** Read `../references/task-contract.md`. Create one exclusive local worktree and branch per PR. Issue independent `general-purpose` owner tasks together; use `mode: background` only while the root performs independent work. Each self-contained prompt includes build, its own `gt` registration when appropriate, self-proof, Bugbot triage, the direct diff-cleanup pass, `/no-comments`, `playbooks/babysit.md`, the no-merge rule, and report format. Every owner keeps a local `decisions.tsv` trail per **show-me-your-work**.
2. **Persist the operator gate.** A plan request is not a go. Start only on explicit go. If the state is ambiguous, follow [User decisions](../references/task-contract.md#user-decisions). Use `ask_user` when available. Otherwise ask one concise plain-text question with numbered choices to start or wait, then end the turn. On go, write the objective, ordered PR list, verification rule, and no-landing constraint to `program-objective.md` in the active session workspace or orchestration store.
3. **Audit with supported recurrence.** Use `manage_schedule` when available for the roughly 30-minute audit and stop it when delivery ends. Each tick re-reads this playbook and `program-objective.md`, checks task status through runtime status/result tools, and judges progress by durable side effects. If schedules are unavailable, use real background watchers and completion notifications while the root works independently. Never claim a sleeper, webhook, or hidden wake chain.
4. **Verify at STACK-READY.** The owner reports STACK-READY with the exact head SHA. The root swarm-verifies that SHA with independent gates, live proof through the project's `.github/skills/verify-*/` skill or existing harness, and a receipts-and-diff audit. Findings go back to the owner. Nothing enters the delivered stack without a clean verdict for its current SHA.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict appends the PR to one linear Graphite stack in verified order or an order the operator specified.
6. **Use one topology writer.** Owners push only their own branches and report tip plus intended parent. The root alone runs stack topology operations such as `gt track -p <current-tip>` and `gt submit --no-interactive --stack`. There is no remote environment selector; all owners and stack operations use explicit local worktrees and branches.
7. **Absorb drift, then re-verify what changed.** The root restacks the chain. When conflicts touch an owner's files, that owner fixes its slice. A restack rewrites SHAs and voids old verdicts. Compare patch IDs; anything that changed returns to step 4.
8. **Deliver the chain.** Return one linear sequence of verified PRs, reviewable bottom-up, with every verdict recorded on its PR. The operator lands it with their own action.

**Choosing between the autopilots.** Use Autopilot-full when independent PRs may merge after the root's verdict. Use Autopilot-stack when merge authority is withheld, work is sequenced, or the operator wants final review.

**Reply:** links to the stack root and tip, a one-line verdict per link, the objective path, and anything parked or excluded with the reason.

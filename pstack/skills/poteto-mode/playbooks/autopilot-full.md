### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean swarm verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. The job is a queue of independent PRs handed over to drive to merged with full autonomy. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge; here each PR's owner carries the lifecycle and the root keeps verification, countersigns, and audits.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay theirs. They review and click, and no owner merges one. A request to state the protocol or plan is not execution. Start only on explicit go. If that state is ambiguous, follow [User decisions](../references/task-contract.md#user-decisions). Use `ask_user` when available. Otherwise ask one concise plain-text question with numbered choices to start or wait, then end the turn. On go, write the exact objective, queue, verification rule, merge authority, and stop condition to a durable `program-objective.md` in the active session workspace or orchestration store. This replaces any hidden cross-turn goal state.
2. **Spawn one owner per PR with the full lifecycle.** Read `../references/task-contract.md`. Create an exclusive local worktree and branch for each owner. Issue independent `general-purpose` task calls together; use `mode: background` only because the root immediately performs independent audit and verification work. Every self-contained prompt includes the program objective, repository and worktree paths, scope, starting ref, build and verification commands, Bugbot triage, the direct diff-cleanup pass, `/no-comments`, restack, `playbooks/babysit.md`, merge gate, and report format. Every owner keeps a local `decisions.tsv` trail per **show-me-your-work**. The owner cannot merge until step 4 returns a clean verdict for its current head.
3. **Run independent owners in parallel and never stack them.** One writer per worktree and branch. Only overlapping work serializes. Self-contained PRs branch from current trunk. Sequenced work is merge-then-branch. A genuinely dependent change may use a short private stack, but the owner must report the dependency and intended parent.
4. **Swarm-verify every merge-ready head.** At the exact merge-ready SHA, fan out independent verifiers per **swarm**. Re-run gates, prove the load-bearing behavior through the project's `.github/skills/verify-*/` skill or existing live harness, and audit the receipts and diff without trusting the PR body. No merge without the root's clean verdict. Findings return to the owner for fix-forward, and every new head gets a fresh verdict.
5. **Merge only the freshly verified head.** The owner merges only after restacking on current trunk and receiving the root's verdict pinned to that SHA. If trunk moves before merge, apply the patch-id rule in `playbooks/shipping.md`; a changed patch requires re-verification. Operator-owned items stop at merge-ready.
6. **Run the root audit recurrence with supported primitives.** Use `manage_schedule` when available for the roughly 30-minute audit and stop it when the queue ends. Each scheduled prompt re-reads this playbook and `program-objective.md`, checks task status through the runtime's status/result tools, and counts only durable side effects such as commits, pushes, PR changes, checks, and stored reports. If schedules are unavailable, use real background watchers plus completion notifications while the root performs independent work. Never claim a webhook, sleeper chain, or wake mechanism the runtime does not expose. A lane past its timebox without a side effect is reconciled, stopped if possible, and replaced with a fresh self-contained task.
7. **Stand down on stop.** Send every active owner a zero-writes instruction when the runtime supports messaging, stop schedules, and cancel background tasks when safe. Record any task that could not be cancelled and verify its branch before accepting late output.

**Reply:** the queue with each PR's owner, state, and head SHA; each verdict and the swarm that produced it; what merged and what each owner took next; countersigns granted and why; open operator gates; the objective path; and where the decision trails live.
